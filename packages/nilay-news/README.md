# Nilay News

<!-- cspell:ignore Geospatial muni -->

A news inbox for hunting, wildlife management, and shooting sports, with publishing to X via [@NilayNews](https://x.com/NilayNews).
It collects RSS and government updates, supports manual review and Jev classification, and posts selected articles through Buffer.
The TypeScript app runs on Cloudflare Workers with D1 storage and Access authentication. Production uses the [Workers Paid plan](https://developers.cloudflare.com/workers/platform/limits/#cpu-time).

## Local development

Follow the [repository setup](../../CONTRIBUTING.md#development-setup).
After installing npm dependencies at the repository root, run:

```bash
cd packages/nilay-news
npm run dev
```

Open <http://localhost:4317>. Collection, search, and manual review work without API keys.
Filter the current list by theme, Jev classification (including 要確認), and duplicate/relation judgment, together with text search. Tick article checkboxes or use 表示中をすべて選択, choose 見送り, 投稿を承認, 保存, or 未読に戻す・承認を解除, then apply the operation. Select-all applies only to currently displayed results; load more articles to include them. Selection clears when switching lists and drops articles that leave the filtered results. Posted articles and articles awaiting a posting result cannot be selected. Dismissed articles can be restored or approved. The server rechecks all selected articles and saves each bulk operation atomically; if any article cannot be changed, the entire request fails and the selection remains for retry.
Local development starts both Workers through Wrangler and uses a local D1 database; regional placement applies only after deployment. Optional integrations use `.dev.vars`; see [.dev.vars.example](.dev.vars.example).

If an article fails before a post draft is prepared, it can be dismissed individually or in bulk; dismissal also clears its failed posting record. To keep the article for another attempt, use 投稿エラーを解除 in its details, then 投稿せずに接続・候補を確認 in settings and enable automatic posting again. Manual approval can also clear such an unsent failure. These actions leave posting disabled until explicitly enabled. Submitted posts and uncertain outcomes still require checking Buffer and X before reconciliation.

## Checks

Run these commands from the package directory:

```bash
npm run typecheck
npm run lint
npm run test
npm run build
```

Tests include a local Worker, D1, and WebCrypto. External APIs use mock responses.
`build` runs a deployment dry run without uploading the Worker.

New Jev classifications and relationship checks record the requested model, the provider's returned model when available, prompt/criteria and routing versions, rubric and policy hashes, exact UTF-8 request hash, and analysis time. Each relationship request also records its comparison article and sanitized-input hash, including checks that permit posting. Details show classifications under 判定の構成と記録 and the last posting check under 投稿前の照合記録. A permitted posting check keeps the original relationship annotation and classification time; a duplicate or uncertain check updates the active posting guard with its own comparison provenance. Failed re-analysis clears the discarded decision’s provenance. Missing provider model information and legacy provenance remain unknown. TypeSafe documents the response model in its [API reference](https://docs.typesafe.ai/api). A stored model probability describes that answer's distribution; it is not measured accuracy.

`npm run evaluate` runs [evaluation/fixtures-v1.json](evaluation/fixtures-v1.json) with deterministic mock responses and compares individual cases with [evaluation/baseline-v1.json](evaluation/baseline-v1.json). The report, request count and diff are saved under the repository's ignored `.local/<date>-nilay-news-evaluation/`. `--fixtures`, `--baseline` and `--output` select other files. Reports distinguish comparison-candidate retrieval misses from relationship errors after successful retrieval, show candidate precision/recall, manual-review rate and duplicate/follow-up confusion, and include all configuration hashes. CI runs the same baseline comparison through the unit tests. `npm run test:e2e` uses an isolated local Worker/D1, signed fixture Access tokens and mocked APIs for settings conflicts, paging/filtering, bulk review, details/retry, publication resolution and keyboard/narrow-screen paths. Install Chromium with `npm run test:install` first.

The initial 12 cases are original synthetic examples with proposed labels, all marked `humanReview.status: "pending"`. They are regression fixtures, not a human-reviewed accuracy dataset; human-reviewed metrics remain null until reviewed cases exist. A human reviewer must inspect the complete evidence and comparison pool, correct the expected decision/relation/source rule and rationale, and record their name and review date. Add difficult real cases only when their text can be redistributed, remove identifying private information, and record curation in the fixture. Increment `fixtureVersion` when cases or labels change. Investigate a retrieval miss before blaming the relationship answer, and inspect the per-case configuration/input hashes when a result changes. For an intentional baseline update, review every changed/deleted case, copy the report's `report` object into the baseline JSON, and rerun tests; preserve pending review status until human review actually occurs.

Live measurement is opt-in and uses only reviewed cases: set separate `NILAY_EVAL_KEY` and `NILAY_EVAL_MODEL`, then run `npm run evaluate -- --live --max-calls 4 --max-input-bytes 16000`. The runner refuses absent request budgets, caps attempted calls at 20 and each request at 32,000 bytes, and stops before transport when either budget is exceeded. Use `--fixtures` and `--baseline` for the reviewed suite and previous live report. Live results are separate from mocked regressions. The evaluator does not load application settings or storage, and never posts. The supplied pending suite makes no live requests.

## Configuration and limits

- [sources.json](sources.json) defines sources, queries, and collection limits. Each Yahoo feed runs at least one hour apart; each Google News and CEEK feed runs at least four hours apart. `collectionOffsetMinutes` spreads the initial phases in JST: Google at offsets 0/120 minutes of a four-hour cycle, CEEK at 0/80/160, and Yahoo at 0/20/40 of each hour. The minute scheduler queues only due feeds independently of the hourly batch. Their persisted next times survive restarts; subsequent periods count from actual completion, so request time and Cron timing cause some drift. Google and CEEK still keep at least 30 minutes between requests to the same host. The regular collection interval for other rolling sources is one hour. Job processing, source intervals, and host cooldowns can delay an individual fetch. Yahoo RSS keeps a limited recent window, so hourly collection reduces missed items but cannot recover entries that have already left the feed. The fixed daily sources and the 鳥獣ニュース roundup retain their daily schedules.
- All displayed timestamps use Japan Standard Time (JST), with a 24-hour clock. Storage and API timestamps remain UTC ISO for comparisons. Existing UTC timestamps embedded in stored warning messages are converted for display.
- Google News and Yahoo RSS and their robots files use the private [feed Worker](wrangler.feeds.jsonc), placed near Tokyo through [Cloudflare regional placement](https://developers.cloudflare.com/workers/configuration/placement/). The main Worker calls it through `FEED_FETCHER`; the relay accepts only exact bundled feed URLs, sends the application User-Agent, and returns redirects and refusal status/Retry-After without following them. Robots checks, caching, source intervals, host leases and backoff remain in the main crawler. There is no alternate route retry. Upstream providers may still reject Cloudflare traffic; successful diagnostics do not guarantee availability.
- A rolling feed deferred without sending a feed request keeps its previous request time and a separate retry time. Refreshing robots.txt or waiting for another query no longer adds a full four-hour delay. Real requests, including failed requests, still consume the source interval; 403/429/5xx backoff and Retry-After are preserved.
- Only articles published within the preceding 24 hours (or today/yesterday in JST when the source supplies only a calendar date) are eligible for automatic classification and posting; the exact 24-hour boundary is included. Known older entries are discarded before storage, and dated old government entries are skipped before detail requests. Google News queries use `when:1d`. Existing older records remain available as history. Unknown, malformed and future publication dates remain for review and cannot use discovery time or feed update time as a substitute. Date-only government entries retain JST-midnight storage plus explicit publication precision; that marker, never a midnight timestamp alone, permits the calendar-day exception. Re-fetching the same URL cannot advance a known valid publication date to revive an old story.
- Sources with `"dailyAtJst": "11:00"` (the gazette, e-Gov, ministry and agency pages, bill indexes, and the shooting and gibier association feeds) are collected once a day starting at 11:00 JST, one source per minute in order, not all at once. The next run is always 11:00 the next day, even if a run started late. Once 11:00 has passed, a run the day missed is due immediately, but earlier days are not caught up. When automatic collection is enabled, the one-minute scheduler queues them independently of the collection interval. An idle automatic job yields to them between items, including between the articles of one classification run, and its remaining sources follow the daily ones. A due staggered RSS feed may run first to preserve its spacing; the daily batch resumes immediately after these few single-request feeds. Manual jobs and jobs in progress are never interrupted. Manual collection also skips a daily source until its next 11:00 run. Other sources, including the 24-hour 鳥獣ニュース roundup, keep their rolling intervals, and regular automatic collection does not include daily sources.
- An RSS source with `"feedContent": "links"` collects each external link in an entry body as its own article, titled by the anchor text or the headline just before it; the entry itself, links back to the feed host, and unsafe URLs are not collected. The 鳥獣ニュース daily roundup uses this and runs at most once every 24 hours with up to 100 links. Linked pages are not fetched, so the roundup's title, URL, and date are kept only as metadata and the article date stays unknown.
- The official gazette (官報) source reads the homepage once a day at 11:00 JST and follows only the full daily TOCs (`/YYYYMMDD/YYYYMMDD.fullcontents.html`) of up to three latest issue days it links, skipping days before yesterday in JST. It saves up to 100 headlines from law, cabinet and ministerial orders, rules, notices (告示), and government reports (官庁報告), each linked to its official page with the issue date, edition, issue number, section, and page. Headlines that share a page are kept as separate articles. Notice pages, PDFs, and full text are never fetched, so only the TOC headline is stored. Public announcements (公告), personnel changes, Diet and Imperial Household items, and government procurement are excluded. Missing or malformed TOCs and unreadable headings appear as warnings. A day with no eligible headings gets a coverage note and no articles. Gazette requests never follow redirects, and older issues are not backfilled.
- Collection follows robots.txt, with exceptions only for sources explicitly marked with `robotsException`: exact Google News search RSS URLs, and, for the enabled gazette source, the exact HTTPS daily TOC URLs above. The user requested the gazette exception, and it does not mean the site granted permission. robots.txt is still read and its crawl delay applied. Exceptions never apply to redirects or any other URL, including notice pages, PDFs, and `/old/`.
- The MAFF press index (`maff-press`) is marked with `"robotsUnavailableStatus": 403`, because MAFF's robots.txt returns HTTP 403 without rules. RFC 9309 (section 2.3.1.3) lets a crawler treat a 4xx robots.txt as unavailable. Only this exact HTTPS URL, while enabled, uses that rule. It is collected once a day at 11:00 JST with at least 3 seconds between requests. The user requested this compatibility rule; it does not mean the site granted permission. Collection proceeds only when the 403 comes from `/robots.txt` directly, not after a redirect. Nothing is cached for the rest of the site, so any other MAFF URL is still refused and the host backs off. The index's own redirects are not followed. If robots.txt returns rules, they apply, including `Disallow` and crawl delays. Any other robots.txt failure stops collection as usual: 401, 429, 5xx, network errors, HTML, or unreadable text. A 403 on the page itself does the same. This rule does not clear an existing host block.
- After an access restriction or network failure, the host cools down. The failure is recorded and reported once, with its HTTP status when known, and stays visible until a later successful fetch. Other feeds on that host send no request during the cooldown; they are deferred and not reported as new failures.
- Jev runs on an explicit classification request, or automatically when automatic classification is enabled. It sends article information and selection criteria to TypeSafe and incurs usage charges. It preserves manual review decisions.
- Between classification items, the scheduler reads all fixed daily source start times in one database query. It loads pending articles only when choosing a new classification batch, and saves each result by reading only that article and up to three compared articles. These reduce database transfers and round trips while preserving the checks for concurrent edits.
- Automatic classification is a separate setting that requires `TYPESAFE_API_KEY`. While no job runs, it queues never-classified articles published within the publication window, newest first, in batches of at most 100 and at most the collection interval in minutes. Each one-minute scheduler run classifies articles one at a time, up to 10. Its first item always starts, even after slow publication checks, so collection keeps its pace; no additional article starts once 45 seconds have passed since the run began, and an article already sent is not cancelled. This is an upper bound, not a guaranteed rate: API response time, a failure, a due 11:00 JST source, or another run holding the job ends the run early, and each run still collects at most one source. A manual job requested during a run is left for the next run, while a manual batch the run started with continues. Existing unclassified articles are included only while still within the publication window. The age is rechecked before each paid call; expired entries in an already queued automatic batch are skipped without a failure. The bulk manual classification button also selects fresh articles first; explicitly selecting an individual historical article still allows a deliberate manual classification. Due automatic collection usually runs first, but one classification batch may follow each finished collection, so collection that takes longer than its interval cannot hold classification back indefinitely. Collection is not queued automatically while no source is enabled. Failed articles are retried only on explicit request, an interrupted automatic batch never sends an already classified article again, and any failed classification pauses automatic batches for one collection interval. Disabling it lets a started batch finish.
- Jev uses one classification distribution for topic relevance and its reason, plus separate topic and priority questions. Candidate probability is the sum of relevant news and related administrative information; excluded probability is the sum of fiction and unrelated news. Either group needs at least 85% to be decided; otherwise the article needs content review. This threshold is a routing rule, not a measured accuracy guarantee. The probability is retained even for review decisions.
- The default selection criteria focus on domestic news and include relevant foreign news. Wildlife and invasive species are limited to birds and mammals. Headlines can be sufficient to classify an article; missing body text alone does not require review. Before classification, keyword search snippets, roundup citation descriptions, explicit related-story sections and collection status metadata are removed from the model input. The stored article remains intact.
- The inbox separates content review for fresh, classified articles (including uncertain duplicate matches) from pending/failed classification, publication dates that cannot be verified, and expired history. Source-designated candidates remain in the inbox under their existing rule. Changing selection criteria invalidates previous automated classifications, preserves manual review decisions and posting history, and automatically reclassifies articles inside the current publication window when auto-analysis is enabled.
- Related-article checks use headline overlap and sanitized excerpts or body leads to shortlist at most three comparisons, reserving a slot for the closest matching posted article. Earlier coverage and posted articles are considered, including a posted article published after a late-arriving story. Jev distinguishes meaningful developments from another outlet’s account or a rewording of the same facts. A follow-up match does not end the search for duplicates among the remaining candidates. An uncertain comparison takes precedence over a follow-up match against another article, so an unresolved possible duplicate cannot be cleared by an older story. Both duplicates and uncertain relations stay out of automatic posting, including manually saved articles, unless explicitly approved for publication; uncertain relations appear in 内容の要確認 for inspection and reclassification. Source-designated candidates retain their explicit exception below. When Jev is configured, each ordinary article without manual publication approval is compared again immediately before sending, against confirmed posts including those just sent in the same round. This uses up to three additional Jev relation requests, without repeating topic classification. A duplicate or uncertain result is retained on the article and the unsent claim is withdrawn. A failed check stops automatic posting; edited article evidence is rejected before sending. This also screens candidates classified before the feature was enabled. Manually saved articles without Jev and the source-designated exception retain their existing behavior. These checks reduce repeat coverage but cannot guarantee model judgments.
- Manual publication approval is a separate review state (`approved`), recorded with its review timestamp and shown in 投稿承認済み. It preserves the Jev decision and relation for inspection, but overrides topic/relation screening, including the final Jev duplicate check, in every posting selection mode. Approval never enables automation or sends immediately: freshness, hourly rounds, sending hours, exact-URL duplicate protection, account checks, and unresolved posting outcomes still apply. Return the article to unread, save it, or dismiss it to remove approval; subsequent eligibility follows the ordinary rules. Reclassification and rubric changes preserve approval. A change to the article evidence during collection revokes it and returns the article to unread. The final send check rejects a changed approval or article. No database migration is required.
- Articles collected from 日本ライフル射撃協会 (`riflesports-news`), 日本クレー射撃協会 (`clay-shooting-news`), or 日本ジビエ振興協会 (`gibier-news`) are post candidates within the same publication window, before and regardless of Jev, as the user requested. The rule matches the exact source IDs an article was collected from, including when another source also collected it; a source name or a mention in the headline does not count. It is derived on every read, so existing articles qualify without being collected again, and nothing is stored or backfilled. Fresh articles appear in the inbox with a 投稿対象（情報源指定） badge and are selected in the "candidates" and "both" posting modes whether Jev has classified them or not, and whatever it decided, including a possible duplicate. Jev still classifies them as usual and its result stays visible separately, but it does not remove them. Dismissing or posting an article, the post history, the posting switch and hourly rounds, and a stop after a failed or unknown post still apply. In the "saved" mode they still need to be saved manually.
- Post hashtags are derived from stored article data whenever a draft is built, without extra requests or changes to stored articles. They come in this order: the original publisher (at most one), up to two places (normally a prefecture and a municipality), then at most two topics. The publisher comes from a ministry or association source's own name, the ministry in charge of an e-Gov item, a publisher label in a Google News, CEEK, or Yahoo headline, or a small list of known news sites. Aggregators and roundups are never tagged as publishers. Places and topics come from the headline, and the excerpt's first sentence adds to them only when it is not a keyword snippet or a roundup citation. Topics also use a current Jev topic. A publisher's name never supplies a place or topic. Anything the data does not state is left out, so a post can have no tags. Posts already stored keep their text.
- [src/data/municipalities.json](src/data/municipalities.json) holds prefecture and municipality names derived from the Geospatial Information Authority of Japan's [muni.js](https://maps.gsi.go.jp/js/muni.js), retrieved 2026-09-28. Wards of designated cities are merged into their city. See the GSI [terms of use](https://www.gsi.go.jp/kikakuchousei/kikakuchousei40182.html).
- Automatic collection, classification, and posting are disabled by default. An hourly posting round selects all currently eligible articles and submits each as a separate post, newest first. Ten eligible articles produce ten posts, rather than a combined post or a ten-hour queue. A durable snapshot fixes the round's article IDs; later arrivals wait for the next round, at least an hour after the previous round began. Each invocation performs at most ten publishing steps within a 45-second starting budget, and an unfinished round continues on later minute ticks without waiting another hour per article. Sending is allowed between 06:00 inclusive and 23:00 exclusive JST and stops on failure or an unknown outcome. A submitted post still awaiting confirmation holds the remaining round until its outcome is known. A due time outside this window moves to the next 06:00; freshness is checked again then. Collection, classification, and confirmation of already submitted posts continue overnight. It reserves no future time while no candidate exists. Manual saves and source-based candidates share the same freshness requirement; a final check after Buffer account verification refuses expired or withdrawn articles and lost claims immediately before submission. The clock is checked again after the database authorization returns, so crossing 23:00 withdraws the unsent claim without disabling posting. This window controls when the app submits to Buffer; Buffer or X may finish delivery later. Check Buffer and X before resuming. Stopping automation does not cancel posts already accepted by Buffer.
- A trusted accepted Buffer ID stays `submitted` for at most six read-only checks over one hour. Checks back off from two minutes to a maximum fifteen-minute interval, survive restarts, and use a new claim token each time so a slow older response cannot replace a newer outcome. Pending confirmation blocks new sends, including after manual posting stops. A terminal remote state, exhausted confirmation budget or deadline becomes `unknown` and needs operator reconciliation. An ambiguous create without a trusted ID is never automatically resent. Settings show the latest API-window remaining/reset observations separately from channel posting limits, including stale, missing and malformed information. Request ordering is reserved durably before the call; reset and Retry-After clocks start when its response arrives. Quota-only updates leave the settings edit token unchanged and follow the existing thirty-second status cache.
- Before enabling posting, use 投稿せずに接続・候補を確認 in the settings (`POST /api/publication/preflight` with `{}`). It sends one read-only query combining channel status and daily posting limits to Buffer, authorized by `BUFFER_API_KEY`, and confirms the channel is X @NilayNews, connected, and set to No Shortening. It requires room under the channel's daily limit and at least eight API requests remaining in every reported rate-limit window, reserving the send and result checks. A malformed present rate-limit header fails closed; successful send and confirmation responses are still recorded when their remaining count is low. HTTP 429 shows the server's Retry-After wait. A send-time limit stops automatic posting; read-only confirmation honors the observed reset and Retry-After within its deadline. Reset times are estimates and do not enable posting; resume manually after checking the connection and result. Limits follow [Buffer's API documentation](https://developers.buffer.com/guides/api-limits.html). It then shows the number of candidates, the exact text of the next post, and anything blocking the start: an unresolved post, no valid next post, or posting already enabled. It never posts, claims, or changes settings, and its result is a snapshot. Enable posting only after reviewing that result; enabling verifies the channel again and fails without changing settings if the check fails. The first post is sent no sooner than 60 minutes after enabling, starting with the newest eligible article in that round. Each send verifies the account and quotas again. Disabling and re-enabling posting clears the unfinished round and starts a fresh one after this delay; importing a snapshot does not resume its transient round.
- [wrangler.jsonc](wrangler.jsonc) requires Access configuration before serving pages or APIs. The separate local entrypoint accepts only localhost requests. Keep deployment values and API keys out of Git.

## Production deployment

[News deployment](../../.github/workflows/news-deployment.yml) deploys pushes to `1.x` that change this package, shared configs, root npm files, or the workflow. It can also be run manually on `1.x`.
A job without credentials runs the checks above. The deploy job then writes the ignored `wrangler.production.jsonc`, validates it, runs a dry run, applies D1 migrations, deploys the private feed Worker, and then deploys the main Worker with its service binding. Manual deployments must use the same order: `wrangler deploy --config wrangler.feeds.jsonc`, then `wrangler deploy --config wrangler.production.jsonc` (both with the same account). The feed Worker has no public/preview URL, database, API key, or external route. Existing settings and jobs require the `0002_auto_analyze` and `0003_automatic_jobs` migrations before API and scheduled initialization can succeed.

Production uses the Worker's default [workers.dev](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/) URL, `https://nilay-news.<account subdomain>.workers.dev`. It needs no custom domain or Cloudflare zone.
The generated config enables `workers_dev`, keeps preview URLs disabled, and has no `route` or `routes`. The tracked [wrangler.jsonc](wrangler.jsonc) keeps `workers_dev` disabled for offline use; any config that enables it must pass the complete deployment checks.

Before the first deployment, create the D1 database and a self-hosted [Access application](https://developers.cloudflare.com/workers/configuration/cloudflare-access/) that covers the entire workers.dev hostname, with an Allow policy for the permitted email addresses. Deploying without it exposes the hostname to the Worker's own Access check only.
Configure the `nilay-news-production` GitHub environment and restrict it to `1.x`:

| Name                        | Kind     | Value                                                         |
| --------------------------- | -------- | ------------------------------------------------------------- |
| `CLOUDFLARE_API_TOKEN`      | Secret   | Account token for Workers deployment and D1; no zone access   |
| `CF_ACCESS_ALLOWED_EMAILS`  | Secret   | Comma-separated email addresses allowed by the Worker         |
| `CLOUDFLARE_ACCOUNT_ID`     | Variable | Cloudflare account ID                                         |
| `NILAY_NEWS_D1_DATABASE_ID` | Variable | D1 database UUID                                              |
| `NILAY_PUBLIC_ORIGIN`       | Variable | `https://nilay-news.<account subdomain>.workers.dev`, no path |
| `CF_ACCESS_TEAM_DOMAIN`     | Variable | `<team>.cloudflareaccess.com`                                 |
| `CF_ACCESS_AUD`             | Variable | Audience tag of the Access application for that hostname      |

Set optional integrations as Worker secrets with `wrangler secret put --config wrangler.production.jsonc`: `TYPESAFE_API_KEY`, `BUFFER_API_KEY`, `SLACK_WEBHOOK_URL`, and `BUFFER_CHANNEL_ID`. Deployment does not enable automatic collection, classification, or posting.

After deployment, a smoke check confirms that unauthenticated requests to `/`, `/app.js`, and `/api/state` redirect to this application's Access login. It does not sign in or request any other host, so it does not verify the Worker, D1, or disabled preview URLs. After the first deployment, sign in and confirm that the inbox and `/api/state` load.

自動仕分けの候補は公開日時・日付精度の索引から新しい順（公開日時、発見日時、記事 ID）に最大 `min(100, pollMinutes)` 件を読み込みます。移行 `0004_article_publication_index.sql` を適用し、既存記事の索引は初回の起動時に 100 件ずつ補完します。日付解析と有効期間は収集時と同じ公開日時規則を使用し、補完も記事更新と同じ同時更新保護を受けます。

記事 API は `GET /api/state` が設定・処理状況・集計のみ、`GET /api/articles` が一覧、`GET /api/articles/:id` が本文・添付・投稿文・判定詳細を返します。一覧は `bucket`（`inbox` / `saved` / `approved` / `review` / `pending` / `dates` / `expired` / `posted` / `dismissed` / `all`）、`query`、`topic`、`analysis`、`relation`、`sort`（`newest` / `priority`）、`limit`（1〜100、既定 50）、`offset` を受け付けます。検索は本文・メタデータ・添付のタイトルも対象とし、一覧へ本文を返す必要はありません。

同順位の記事は発見日時、記事 ID で順序を固定します。次ページは応答の `snapshot` を渡し、記事の同時更新や 30 秒の有効期限により `409 article_page_conflict` となったら先頭へ戻ります。有効なページ間では最初のページの時計を用い、公開日時の境界をまたいでも重複や欠落を防ぎます。定期更新と操作後の再取得は新しい `snapshot` で現在の位置を読み直し、表示中に残る記事の選択を保持します。現在の位置が件数を超えた場合は末尾のページへ移ります。画面は 50 件単位で移動し、一括選択は表示中のページを対象にします。移動・絞り込み時に選択を解除します。本文は選択時に取得し、関連記事も別途取得します。

`npm run benchmark:articles -w @sasakiuri/nilay-news` は隔離されたローカル D1 へ 1,000 / 10,000 件の同じ構成の fixture を用意し、従来の全記事応答相当と新しい状態＋先頭 50 件について、3 回の時間・応答 bytes・D1 `rows_read`・転送記事行数を JSON で報告します。集計や検索には SQL 内の走査が残るため、応答の上限とデータベースの読取量は区別してください。実環境のレイテンシはこの測定から推定しません。
